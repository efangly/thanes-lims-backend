# Redis as a read-through Cache for Refresh Tokens and Location Full Path

The system has no caching layer at all today: Refresh Token revocation is checked with a Postgres read on every `/auth/refresh` call, and a Sample's Location Full Path is recomputed with a recursive CTE on every read that needs to display it. Neither is expensive enough on its own to force this change, but both are on hot, frequent read paths, and a managed Redis instance is already provisioned (`REDIS_URL` in `.env`, shared with the MinIO deployment) and unused. We're wiring it in now for these two cases rather than waiting for either to become a measured problem.

In both cases Postgres stays the source of truth; Redis is strictly a read-through Cache behind a single generic port, `internal/ports/cache.Cache` (`Get`/`Set`/`Delete`), implemented once in `internal/adapters/redis` and reused by both call sites rather than modeling two bespoke caches. Keys are namespaced by prefix (`refresh:{token_hash}`, `location:fullpath:{id}`) in one Redis logical DB — multiple DB indexes were considered and rejected as unnecessary ceremony at this scale, and not universally supported by managed Redis offerings.

The two use cases deliberately fail in opposite directions, because the cost of being wrong is opposite:

- **Refresh Token Cache Entry** (full row: family id, expiry, revoked, family_created_at) is **fail-closed**. If Redis is unreachable when checking a Refresh Token, the request is rejected rather than falling back to trusting an unverified token — a false rejection is an inconvenience, a false acceptance of a revoked token is a security hole. The entry is written on Login/Rolling Refresh and deleted on revocation, so Redis and Postgres are kept in lockstep rather than relying on TTL alone to converge them. `RevokeAllForUser` (Reuse Detection, logout-all, Role change) reads the affected Refresh Token hashes from Postgres first, then deletes each key from Redis in a loop — no separate `user_id → token_hash` index is kept in Redis, since revoke-all is a rare security-path operation, not a hot path, and an extra denormalized index would only add another place for Redis and Postgres to drift apart.
- **Full Path Cache Entry** is **fail-open** and **TTL-only** (15 minutes, matching `JWT_ACCESS_TTL`). On a cache miss or a Redis outage, Full Path is simply recomputed from Postgres as it is today — Location data changes rarely once a Cabinet's tree is set up, so a bounded staleness window was judged an acceptable trade against the complexity of walking a subtree to invalidate every descendant's cached path on rename/move/delete.

Access Tokens are explicitly out of scope: they remain unrevoked-by-design per [ADR 0002](./0002-normalized-rbac-with-jwt-embedded-permissions.md), bounded only by their 15-minute TTL. Adding a blacklist for them would be new functionality, not something this change was asked to cover.

Client library: `github.com/redis/go-redis/v9`. Config: the existing `REDIS_URL` env var, following the same single-connection-string pattern as `DATABASE_URL`. No `docker-compose.yml` is introduced — the project has never had one for any dependency (Postgres, MinIO, Oracle included) and local dev already points at the shared remote instances via env vars. Integration tests use `testcontainers-go/modules/redis`, matching the existing Postgres integration-test pattern (`-tags=integration`).

**Status**: accepted
